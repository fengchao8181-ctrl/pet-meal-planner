# 留存阶段一设计：每日喂食打卡 + 健康周报（「有爱」主题）

- 日期：2026-09-13
- 状态：已按评审定稿（2026-09-13 二次确认）
- 产品定位转变：从「一次性餐单生成工具」→「让客户感受到自己在认真爱它」的宠物养成助手

## 0. 核心主题与产品原则

- **核心主题：「有爱」**
- **定位主张：用专业喂养，用有心陪伴。**
- **落地原则（双层表达）**：底层健康数据绝对客观可信；前端情绪表达尽情暖心。两条线在 UI 上分层并存、互不污染——情绪的渲染不稀释营养数据与兽医参考的可信度。
- 全程把用户称作「它的家人」，把宠物称作「你的小可爱」；按钮/推送语气暖心化。

## 1. 背景与目标

现状问题是**留存缺失**：用户生成一份餐单，得到结果后即刻离开，产品是一次性的。本次目标是建立第一个「让人每天有理由回来」的习惯闭环，并让「有爱」成为贯穿产品的情感基调，让用户每次完成动作都感到「我在被看见、我在认真爱它」。

目标校验：上线后连续 7 日回流率、每周日周报打开率，作为留存优化的北极星。

## 2. 范围（做 / 不做）

### 本阶段做（MVP）
- 每日喂食打卡（一键完成、近 7 天打卡状态、连续天数）
- **打卡心情一戳**（5 表情：开心/犯困/傲娇/安静/闹腾，随打卡记录，进入周报温度）
- **连续里程碑庆祝**（连续 7/30 天自动弹出庆祝动画 + 徽章，复用 streak 数据）
- 健康周报（每周日生成：完成率 + 平均执行度 + 可选体重趋势 + **情感化文案** + 下周建议）
- **结果页「去打卡」入口**（把结果页引导转向免费留存）
- 打卡与周报数据落库（扩展仓储，Mock 先跑通，飞书可替换）
- 页面与后端接口、纯逻辑单测、页面事件流冒烟

### 售后处理（沿用已实现、阶段一弱化/不深化）
- 结果页「订阅解锁卡」：**保留但弱化**（不删代码）——检测到进入留存流程后侧重留存引导，避免"留一手"反噬留存。
- 订阅页优惠 banner / 多档 SKU：**阶段一不深化**（不删已实现，只暂不做进一步转化投入）。

### 本阶段不做（明确排除）
- 宠物名片 / 健康分 / 纪念日 / 宠物照片上传（后续阶段，照片涉及上传链路复杂度、先稳闭环）
- 微信订阅消息主动下发（需正式模板 ID，本阶段仅做「提醒授权」占位 + 推送策略备料，见 §8）
- 每日餐单推送、目标驱动、社交分享、内容百科、社区

## 3. 信息架构与页面

新增 2 个页面（接入 tab 或结果页入口）：

```
pages/checkin/index         今日喂食打卡
pages/report/index          健康周报
```

- `checkin`：今日是否已完成、一键「今日已喂」+ 心情一戳、连续天数徽标、里程碑庆祝弹窗、近 7 天打卡格点、可选填本次喂食执行度与体重、「开启每日喂食提醒」授权占位入口。
- `report`：本周报告卡顶部**「本周用心值 💗」**（可展开看客观口径）+ 完成率/执行度/趋势/情感化小结 + 历史周报列表。
- 入口：结果页 `result` 增加「去打卡」按钮；`app.json` 注册两页；`checkin` 顶部放「每周报告」入口，`report` 反向回 `checkin`。

## 4. 数据模型

采用「新用户无档案也允许打卡（体验门槛最低）」，以 `openid`/设备本地 id 作为打卡者键，周报按周生成。

```
CheckinRecord {
  id          string   // uuid
  petKey      string   // 打卡主体键（当前取生成餐单时的 petName+breed 组合，或本地固定键）
  date        string   // YYYY-MM-DD，本地时区当日
  fedAt       string   // ISO 完成时间
  mood        string   // 心情一戳：happy/sleepy/proud/calm/naughty（可空）
  execPct     number   // 本次喂食执行度 0-100（可空）
  weightKg    number   // 可选当日体重（为周报趋势提供数据）
  createdAt   string
}

WeeklyReport {
  id          string
  petKey      string
  weekStart   string   // 该周周一 YYYY-MM-DD
  weekEnd     string   // 该周周日 YYYY-MM-DD
  checkRate   number   // 完成率 %（打卡天数/7）
  streakDays  number   // 截至周末连续打卡天数
  avgExec     number   // 平均执行度 %（有执行度记录时）
  weightTrend []{date,weightKg}  // 体重点列
  moodTop     string   // 本周出现最多的心情（可空，"本周它最常犯困"）
  loveScore   number   // 本周用心值 0-100（由连续天数+执行度+体重记录折算；可展开看口径，纯情绪层）
  summary     string   // 一段情感化自然语言小结（"你和豆豆已经一起坚持了 N 天"）
  tips        string[] // 下周建议
  createdAt   string
}
```

**周报不独立存原始数据**，由最近的打卡记录在生成时计算并缓存为 `WeeklyReport`；周内重复查看复用缓存，周日/次周一重新生成。

## 5. 后端接口

```
POST /api/checkins            body:{petKey,date?,execPct?,weightKg?} → {record}
GET  /api/checkins?petKey=&from=&to=        → {records:[...]}
GET  /api/reports/week?petKey=&date=        → {report}    // 无则根据记录生成
GET  /api/reports                  ?petKey= → {reports:[...]}  // 历史周报
```

- 同 `petKey+date` 已打卡则**幂等**：重复提交仅更新 `execPct/weightKg`，不重复计天数。
- `date` 缺省为服务器本地当日；周界定为「周一为一周起点」。

## 7. 周报生成规则（纯逻辑，可单测）

1. 取 `[weekStart, weekEnd]` 区间 `listCheckins`；`streakDays` = 截至周日的连续打卡天数。
2. `checkRate = round(有打卡天数 / 总天数 * 100)`。
3. `avgExec = round(有 execPct 记录的平均值)`，无则 null。
4. `weightTrend = 有 weightKg 的 {date,weightKg} 升序列表`；若 ≥2 点则附「较上周 ±x kg」。
5. `moodTop` = 本周出现最多的 mood，无记录则 null。
6. `loveScore`（本周用心值，纯情绪层，可展开看口径）= clamp( round( 连续天数占比·40 + 平均执行度·40 + 体重记录次数/7·20 ), 0, 100 )；口径文案："本周打卡 X/7 天 · 平均执行 Y% · 记录 Z 次体重"。
7. `summary`：情感化叙事 = 问候已坚持天数"你和{昵称}已经一起坚持了 N 天"+ 按完成率分档句子（≥5 天「规律喂养，状态稳定」；3-4 天「存在间歇，建议固定时段」；<3 天「先从每顿打卡这个小目标开始」）+ 结合 `moodTop`/`weightTrend` 增补一句（有则"本周它最常犯困""它比上周轻了 x kg"）。
8. `tips`：通用 2 条 + 当执行度偏低时追加 1 条「按每日热量等比递减，别一次减太多」。

## 8. 推送与触达策略（含企业每日 H5+小程序触达）

### 8.1 平台机制（决定打法）
- **小程序订阅消息**：分两类——**一次性订阅**每授权一次发 1 条；**长期订阅**仅对政务民生/医疗/交通/金融/教育等特定类目开放，宠物喂养**无法申请不限次数**。且下发需**正式模板 ID**（带 `WXPAY_*` 相关或独立模板）。
- **公众号服务通知（H5）**：引导关注公众号后，**每天可推 1 条**，属另一主体/资质与不同运营。

### 8.2 触达通道策略：企业每日推送 = H5 每日一条 + 小程序关键触发
**确认运营模型：企业（品牌）作为客户宠物生活的「常在陪伴者」，通过双通道做到「每日触达」，让客户与品牌之间建立一天一天的亲密感，而不是事件触发的一次性打扰。** 双通道就近触达，把有限而珍贵的触达用在刀刃上：
- **H5（公众号服务通知，可每日一条）**：承担「企业每日推送」的主力——早间喂食问候、周报出炉提醒、里程碑庆祝、换菜灵感、健康小贴士。**凡指向"每天都能触达客户"的柔性关怀都走 H5**，做高频、稳定的每日陪伴。
- **小程序（订阅消息，一次性/稀缺，需正式模板 ID）**：只推最高价值的**关键触发**——用户自设喂食作息提醒、周报生成、里程碑毕业、体重显著变化。**凡指向"重要时机、用完即止"的硬提醒都走小程序**，把每 1 次授权名额用在最值得的时刻。
- **双通道分工原则**：H5 管"每天在"，小程序管"关键时到"；两厢配合，既不打扰又不缺席。

### 8.3 让每次触达贴近客户（「有爱」人设）
1. **宠物第一人称语气**：不是"该喂粮了"，而是"豆豆在等你开饭啦 🐾""今天豆豆吃掉了 85%，它很满足"。
2. **个性化称呼**：每条都带宠物昵称（豆豆/汤圆）+ 具体数字（吃掉 85%、坚持 N 天），像真人记得它。
3. **时机=情绪最高点**：在**建档后、首次打卡后、周报生成时**要授权（`wx.requestSubscribeMessage`），情绪高涨时最不犹豫，也就拿到下一次触达名额。

### 8.4 推送与付费的关系
**真实推送本身就该是订阅的理由**：订阅用户获"每日配方 + 周报 + 更高频触达"，免费用户得"里程碑 + 喂食提醒"关键触达。让推送的亲密感成为续费动力，弱化对解锁卡/折扣 banner 的依赖。

### 8.5 阶段一落点（不真正下发，先备料）
- `checkin` 页「开启每日喂食提醒」授权占位按钮：引导 `wx.requestSubscribeMessage`，预留 templateId 配置位 `config.js`，回调成功后展示「已开启」并持久化本地，作下阶段真实推送的入口支架。
- 在代码中预置**推送内容库**（喂食提醒 / 周报通知 / 里程碑 / 暖心关怀 4 类，已按 8.1-8.3 人设写好模板文案与触发时机），当模板 ID 与主体资质就绪后可直接启用。
- H5 公众号通道不在阶段一接入（需公众号主体），仅在设计层面预留，避免提前建设运营资产。

### 8.6 真实推送接入的计划衔接
§8.1-8.5 是策略与阶段一备料；「进入实现计划」的落地路径（正式模板申请 → `config.js` 启用 → 小程序服务端 `sendSubscribe` 接口 → 公众号 H5 access_token 与每日定时任务 → openid 打通与推送偏好 → 频率控制与退订 → 联调验收）见独立文档 `docs/superpowers/plans/2026-09-13-push-implementation-plan.md`。
